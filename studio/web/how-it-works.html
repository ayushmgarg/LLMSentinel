How it works

How a comparison runs

Nothing here is a judgement about the answer the model gives. The guard works on the text that reaches the model and on the tool calls that come back, and every step leaves a trace you can read.

Open the console What it does

How a comparison runs

  1. 01

    Retrieve

    Files are split into passages (JSON by string leaf, keeping its path), and the passages that best match the question are retrieved with TF-IDF.

  2. 02

    Inspect

    Each passage and every tool description from connected servers is normalised and scored. The span-aware transformer decides at its dev 1%-FPR threshold; the rule engine explains, decodes hidden payloads and also flags at its 0.1%-FPR band. Each tool's declaration is also compared with the digest pinned when it was approved.

  3. 03

    Isolate

    Flagged sentences, hidden comments and encoded blobs are removed; if what remains is still suspicious, the whole passage is withheld. A tool whose description is flagged, or that changed after approval, is quarantined.

  4. 04

    Answer and gate

    The same system prompt and question go to your model twice. Tool requests are classified; with Sentinel, the capability policy allows, confirms or blocks them.

What counts as untrusted

Three surfaces reach the model without anyone on your team writing them, and each is scanned as its own channel, because the same sentence means different things depending on where it arrived from.

Retrieved documents

Wiki pages, tickets, files, web pages. Split into passages; the passages that match your question are what the model actually reads.

Tool results

Whatever a tool returned. JSON is split by string leaf and each leaf keeps its JSON path, so a finding points at a field and not at a blob.

Tool manifests

The names, descriptions and parameter descriptions an MCP server advertises. The agent reads them before any question is asked, which is what makes them worth poisoning.

In the console, a dropped file is read by its type, and pasted text says what it is: the dropdown sets the channel, so a tool result stays a tool result even when it does not parse as JSON.

When it flags

Two components, one rule

A passage is flagged when the fine-tuned classifier crosses its threshold, or when the rule engine crosses a stricter one. The transformer generalises to wording the rules never saw; the rules explain themselves, decode hidden payloads, and hold the line where the classifier is unsure.

Both thresholds were selected on the development split at a fixed false-positive budget and are never re-tuned per run. The values in force on this machine are printed above.

What a finding carries

  • the source, channel and JSON path it came from;
  • the exact span that fired, in the normalised text;
  • the rule trace, as [family/rule score] explanation;
  • evidence from normalisation: zero-width characters, bidi controls, HTML comments, decoded base64.

If the detector itself degraded, the finding says so, and the decision is taken one step stricter rather than being trusted.

What isolation removes

Isolation is not redaction of everything suspicious: the useful half of a poisoned page is usually still the answer to your question. The guard removes the least it can, and then checks its own work.

  1. 01

    Segment

    The passage is split into sentences, HTML comments and encoded blobs.

  2. 02

    Cut the worst first

    The most suspicious segment is removed, and what remains is scanned again — under a stricter criterion than the one used to flag it.

  3. 03

    Repeat, or withhold

    Cutting continues until the remainder is clean. If it never becomes clean, the whole passage is withheld rather than forwarded.

  4. 04

    Mark the gap

    The model sees a marker where text was removed, so it knows something was withheld. The marker is excluded from re-scanning, so the guard never flags its own annotation.

A tool whose description is flagged, or whose declaration changed after it was approved, is quarantined instead: it is left out of the guarded run entirely.

How an action is decided

The detector is probabilistic and advisory. The gate is a deterministic table: a tool is classified by its worst possible effect, the context’s risk selects a column, and the cell is the outcome. Risk chooses the column; it never changes what the column says. Nothing in the project executes a tool — the decision is an object, and the console shows it.

A tool nobody classified counts as a sensitive read, not as read-only: an unknown tool is an unreviewed tool. A destructive action is blocked at risk 0.0, because a detector’s false negative should not be the only thing standing between a document and a deletion. A degraded detector escalates every outcome one step.

What happens after the verdict

Review, not rewriting

Every scan is recorded locally in an append-only history. A reviewer who disagrees with the guard adds a label and a rationale beside the original verdict; the verdict itself is never edited, because a record that can be rewritten is not evidence. Uncertain cases land in a queue, and a reviewed case can become a regression fixture — sanitised, with hosts rewritten to reserved .invalid names and secret-shaped tokens redacted.

Candidate rules, proposed not applied

Phrases that keep appearing in confirmed injections, or in detections no rule could explain, are mined into candidate rules. Each candidate reports what it would match on the development split before anyone approves it, and an approved candidate runs as a second opinion in a separate advisory engine.

It is not part of the scored detector, so no measured number moves because the guard saw new traffic. Promoting a candidate means rebuilding the corpus and re-running the evaluation: the loop shortens finding a rule, never accepting one.

Reading a run honestly

Reading results honestly

  • The simulator is not a language model. It obeys planted instructions by pattern, so it shows how the pipeline works, not how accurate the detector is.
  • Small local models do not always follow injections. An unguarded answer with no compromise is a real outcome, not a broken demo.
  • Attack success is judged by objective signs: a leaked confidential code, a reserved .invalid attacker address, a dangerous tool request, or a planted claim in the answer.
